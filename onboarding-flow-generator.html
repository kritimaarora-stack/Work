01The problem

Onboarding got redesigned from scratch, again and again.

When teams designed onboarding independently, the same problems kept coming back across products, and designers kept solving problems another team had already solved.

  • Same data, asked twiceInformation collected again and again across different flows.
  • Friction up frontFields that could wait are asked before users get any value.
  • Patterns that don't matchUsers switching between products meet different interactions for the same task.
  • Knowledge that doesn't travelWhat we learned lived in scattered files, people's memories and old Figma screens.

What if onboarding design could learn from every flow we've already built?

02How we built it

No engineers. My designers and I built it ourselves.

Onboarding work was eating my team's time on repetitive decisions. Instead of asking for engineering time, we built the tool ourselves in Kiro, an AI coding environment, so designers could turn what they already knew into a working system.

The team's job shifted from redrawing the same forms to documenting what works: flows, patterns, rules and insights that the system can reason from.

03How it works

Four agents, one shared memory.

The knowledge base

  • Documented flows
    onboarding_flows.jsonWhat already exists?
  • UX patterns
    patterns.jsonHow are problems being solved?
  • Design rules
    guidelines.jsonWhat should a good flow do?
  • Cross-product learnings
    insights.jsonWhy do decisions work or fail?

Every agent reads from the same four files, and they grow with every flow we document.

The agents

  1. 01
    Research Agent

    Understands the problem before any screen is proposed: precedents, similar users, constraints and known risks.

    What should actually be solved?
  2. 02
    Flow Architect

    Turns research into stages: what goes first, what can wait, where the flow branches.

    What should the journey look like?
  3. 03
    Interaction Agent

    Chooses inputs, groups fields and spots auto-fill and verification states.

    How does it become an interface?
  4. 04
    Optimization Agent

    Reviews everything against our rules and flags redundant fields, early asks and missed auto-fill.

    Is it good enough? If not, revise.

It reviews itself. If the Optimization Agent finds problems, it sends the flow back to the Flow Architect to revise, up to two times, before returning a final recommendation across research, flow, interaction and optimization.

04In practice

Used on a real flow: HR system onboarding.

We used the generator to draft the new-user onboarding for our human resource management system. A typical requirement, and what the system did with it:

The requirement“Design self-onboarding for 500 warehouse candidates per day. Candidates need Aadhaar verification, employment details, education details and bank information.”

The instinct: one long form

  • Every detail asked up front
  • Name and date of birth typed by hand
  • Same steps for every user
→

What the system recommended

  • Auto-fill name and date of birth from Aadhaar
  • Defer employment and education details so they don't block onboarding
  • Keep each step short for high volume
  • Simpler patterns for low-literacy users
05Why it matters

Don't make every designer solve the same problem from zero.

  • Learn from every flowEach documented flow becomes memory the system reasons from.
  • Consistency by defaultPatterns and rules apply the same way across every new flow.
  • Catch issues before design startsAvoidable UX problems surface before anyone opens Figma.
  • Solved problems stay solvedWork done once becomes the starting point for the next team.
